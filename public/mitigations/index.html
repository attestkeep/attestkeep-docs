Known temporary mitigations

Some CVEs are published before a fixed version exists, with a temporary measure to take until it does. Attestkeep can show that measure beside the CVE, list the images that carry it while no fix is released, and read the pods running them to say whether the measure is in their spec.

Both switches are in Settings › Scanning › Mitigations, for administrators, and both are off as shipped.

Off, nothing changes. With both switches off, no mitigation, band or pod check appears in the console or the API. On, counts, policy decisions and evidence packages still do not change. Attestkeep never applies a mitigation and never changes a pod.

The two switches

SwitchWhat it does
Show known temporary mitigationsShows a listed CVE's mitigation on Vulnerabilities and in the Images drawer, and the Fix not released yet band.
Check running podsWhen such a CVE or image is opened, reads the spec of each pod running it: the pod check. It can be on only with the first switch; turning the first off turns it off too.

A change is written to the audit log as settings_change. Your own page follows at once after you save; other open tabs and other people see the change after reloading the page.

The list

The list ships with Attestkeep, inside the operator binary, and changes only with a release. Each entry names its CVEs, says what to do until the fixed version is installed, cites its sources and gives the date it was last reviewed. The note appears in a CVE's detail on Vulnerabilities and beside the finding in the Images drawer.

CVEMitigationSourcesReviewed
CVE-2026-114938Turn off the HotSpot Base64 intrinsic. Until the JDK is upgraded past the affected versions (17.0.21.0.3, 21.0.13.0.3, 25.0.5.0.3, 27.0.1.0.3 and earlier), start the JVM with -XX:-UseBASE64Intrinsics, for example by adding it to JAVA_TOOL_OPTIONS. Only x86-64 CPUs with avx512f, avx512bw, avx512vbmi and bmi2 are affected; ARM64 is not. This is a temporary measure, not a fix. Measure the performance effect.OpenJDK advisory 2026-11-17, Red Hat CVE-2026-114938, Wiz: CVE-2026-114938 (Java4Shell), NVD CVE-2026-114938 (CWE-122), JVM TI: JAVA_TOOL_OPTIONS2026-11-19

The note rides on a finding. An image Attestkeep has not scanned, such as one in a namespace the admission webhook bypasses, shows nothing, and no finding does not mean not affected.

Fix not released yet

With include_unfixed off, the default, a finding with no released fix is kept out of every count and list. A CVE on the list among those findings is the one that most needs to be seen, so it gets a band of its own above the Vulnerabilities list: the CVE, the worst severity among its images, how many images carry it, the mitigation and, with the pod check on, the pods. The Images drawer shows the same band for its image.

  • The band is in no count, no policy decision and no evidence package.
  • On Vulnerabilities it does not follow the page's filters and search: it always lists every such CVE.
  • If the band cannot be read, the page is shown without it and the operator logs why.

Pod check

With Check running pods on, opening such a CVE on Vulnerabilities, or an image that carries one in the Images drawer, reads the cluster's pods at that moment and lists every container running an affected image, matched by the digest the node reports. Nothing is stored.

Pod specMeaning
Found in pod specThe flag is in JAVA_TOOL_OPTIONS (read by the JVM itself), in JDK_JAVA_OPTIONS (read only by the java launcher, so not by a JVM started another way), or among the options of a java command the container runs: its command, or a java command inside its sh -c script. A flag after -jar <file> or after the main class is the application's argument and does not count.
Found in JAVA_OPTS_APPEND, Found in JAVA_OPTSThe flag is in a variable only the image's start script reads. Whether it reaches the JVM depends on that script.
Found in container argsThe flag is in arguments handed to the image's entrypoint, or to a program that is not java. Whether it reaches the JVM depends on that program.
Not found in pod specThe pod spec does not name the flag. This does not mean unprotected: see what the check cannot see.
Cannot tellPart of what the JVM will see is not in the pod spec as text, and the reason is named: envFrom is not read; the variable comes from a reference (valueFrom) that is not read; a $(VAR) reference is not expanded; an options file is used (@argfile or -XX:VMOptionsFile); the flag and its opposite (-XX:+UseBASE64Intrinsics) are both set; or the flag is in a shell script but not among a java command's options.

_JAVA_OPTIONS is read only for the opposite flag: -XX:+UseBASE64Intrinsics there, with the flag set elsewhere, makes the answer Cannot tell. The flag in _JAVA_OPTIONS alone is not counted.

Which containers are listed

  • Every running container of a running pod, init and ephemeral containers included.
  • A container in a crash loop, listed as waiting to restart.
  • An init container that completed, listed as init container, ran and finished with the time.
  • Not listed: a pod that has finished (Succeeded or Failed) or is being deleted, and any other container that has stopped and will not be started again.

The read stops at the limits of the deny list's What if (denyListWhatIfLimits, by default 20 seconds or 20,000 pods) and then says the answer is partial.

What it reads

  • Pod objects only: each container's env, envFrom, command and args, and its status. A variable's value is read in memory only to answer whether the flag is in it. The answer names the variable, never its value, and the value is not logged or stored.
  • Never a Secret or a ConfigMap. A variable that comes from one is Cannot tell.
  • No new permission: the operator's existing cluster-wide pod read covers it (see What runs in your cluster).

What the check cannot see

  • A flag set inside the image: in its ENV, or added by its start script. The pod spec does not carry either, so such a container reads Not found in pod spec.
  • Values from envFrom or valueFrom: Cannot tell.
  • Options files (@argfile, -XX:VMOptionsFile): Cannot tell.
  • What a start script does with JAVA_OPTS_APPEND, JAVA_OPTS or the container's args: the answer says it depends on the script.
  • The JVM's own flags at run time. The check reads what the pod spec gives the container, not the running process.

Worth a look

The pod check's Last restart column shows a container's restart count. When the last termination was SIGSEGV or SIGABRT (exit 139 or 134) and the entry's CVE is a memory-corruption one, as CVE-2026-114938 is (CWE-122), it reads Worth a look with the signal, the exit code and when.

  • It is not proof of an attack. Most crashes are not attacks, and an attack need not crash anything.
  • An out-of-memory kill (OOMKilled) is never flagged, and neither are SIGKILL and SIGTERM (137, 143).
  • The kubelet keeps only the last termination, so an earlier crash is not seen.
  • It is shown in the console only: no notification, and nothing in the evidence package.

With Falco

A temporary mitigation acts before anyone exploits the CVE. If you run Falco, the rule template Java process spawned a shell (Falco › Rules › From template) raises an event when a JVM starts a shell in a container, and says what it does not catch. See Runtime events.

API

  • GET /api/v1/settings/mitigations (any signed-in account) and PUT (administrators), body {"hints": true, "check_pods": false}. check_pods without hints, an unknown field, a value that is not true or false, or anything but one JSON object is refused with 400.
  • GET /api/v1/vulnerabilities and GET /api/v1/images/detail: with hints on, a listed CVE's row carries mitigation (id, title, text, sources, reviewed_at), and the answer carries unfixed_with_mitigation, the band.
  • GET /api/v1/mitigations/check?cve=CVE-…, or ?digest=sha256:… repeated up to 50 times, not both: read_at, pods_inspected, partial, note, hint_ids and rows (digest, namespace, pod, container, hint_id, state, source, reason, running, restart_count, finished, finished_at, crash). No field carries a variable's value. 409 while the pod check is off; 400 for a malformed CVE id or digest.
