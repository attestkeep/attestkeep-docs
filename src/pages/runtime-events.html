Runtime events from Falco

Attestkeep decides what may run. Falco watches what a container does once it is running. This integration is the join between them: your Falco's events arrive here, are filed against the image that produced them, and your runtime rules decide what each one leads to.

Attestkeep does not ship, install or run Falco. The detection is yours; this is a place to put what it found and decide what follows. An event changes an admission decision only when you ask it to: a block rule opens a runtime block on the image, and only a policy with runtime.enforceBlocks: true refuses new pods of a blocked image. A broken alert stream cannot break your cluster — no events means no new blocks, never a refusal. Runtime behaviour detection stays outside what this product does, for the reasons on what Attestkeep does not do.

What you need

  • Falco, installed however you install it. Written against Falco 0.45 and the upstream falcosecurity/falco Helm chart; older versions are not claimed.
  • Network reach from the Falco pods to the operator's Service on the integrations port, 8444 by default. Both usually live in the same cluster, so this is a ClusterIP address and no ingress.

Falco sends each event itself, from its own http_output, straight to the operator. Nothing sits in between: no Falcosidekick, no token.

How Falco proves who it is

Falco's http_output cannot send a header, so there is no token. It can present a client certificate, and that is the whole of the authentication:

  • With the integration on, the operator creates a small CA of its own (CN=attestkeep-falco-ca, ECDSA P-256, five years) and one client certificate for Falco (CN=falco, client authentication only, one year), in the Secret <release>-falco-mtls in the operator's namespace.
  • The operator serves POST /api/v1/integrations/falco on its own TLS port, the integrations port, and nothing else there. The handshake requires a client certificate signed by that CA, and the endpoint then requires its CN to be falco. The API port does not serve this route at all.
  • The server side is the operator's existing serving certificate, the one the admission webhook uses, whose name is the Service, <release>.<namespace>.svc. Falco verifies it with the ca.crt from the bundle.

1. Turn the integration on

integrations:
  port: 8444
  falco:
    enabled: true
helm upgrade attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  -n attestkeep -f values.yaml

The chart opens the integrations port on the pod and the Service, and the operator creates the Secret on start. With enabled: false, the default, there is no listener, no CA and no Falco section in the console.

2. Download the certificates

In the console, Settings > Integrations (admins only) shows the endpoint URL, when Falco's client certificate expires and when the last event arrived. Download certificates gives attestkeep-falco-mtls.tar.gz with three files:

FileWhat it is
ca.crtThe CA that verifies the operator's serving certificate.
client.crtFalco's client certificate.
client.keyIts private key. Keep it private: whoever holds it can post events your runtime rules act on.

The same bundle is GET /api/v1/integrations/falco/bundle (admin). Every download is written to the audit log.

3. Put them in the Falco namespace

tar xzf attestkeep-falco-mtls.tar.gz
kubectl -n falco create secret generic attestkeep-falco-client \
  --from-file=ca.crt --from-file=client.crt --from-file=client.key

4. Point Falco at the operator

Values for the upstream falcosecurity/falco chart. certs.existingClientSecret is that chart's own value for an existing Secret holding client.crt, client.key and ca.crt for outbound HTTP output mTLS, and the paths are the ones its README uses for it:

# values for the falcosecurity/falco chart
falco:
  json_output: true
  http_output:
    enabled: true
    url: https://attestkeep.attestkeep.svc:8444/api/v1/integrations/falco
    mtls: true
    ca_cert: /etc/falco/certs/client/ca.crt
    client_cert: /etc/falco/certs/client/client.crt
    client_key: /etc/falco/certs/client/client.key
certs:
  existingClientSecret: attestkeep-falco-client

The URL is the one the console shows: https://<release>.<namespace>.svc:<integrations.port>/api/v1/integrations/falco. json_output: true is required — the endpoint reads Falco's JSON alert.

5. Check it arrives

Trigger any rule — kubectl exec a shell into a pod, for example — and look at Settings > Integrations > Last event, or at the Falco section, which appears in the sidebar once the integration is on. GET /api/v1/runtime/status answers the same question: enabled, last_event_at, events_24h.

Rotating the certificates

Rotate on the same page, or POST /api/v1/integrations/falco/rotate (admin, audited), issues a new client certificate from the same CA. The previous one is not revoked: it keeps working until its own expiry, so Falco keeps delivering while you download the new bundle and replace the Secret in the Falco namespace. Rotating the Falco CA itself is not offered in this version.

The ca.crt in the bundle is the CA of the operator's serving certificate, and that pair rotates about once a year. The bundle carries the previous CA as well as the current one, so Falco keeps connecting through one rotation; it does not through the second. As soon as the CA has changed since the bundle was last downloaded, Settings > Integrations says "Certificates changed on <date>": download the bundle again and replace the Secret in the Falco namespace before the next rotation.

Upgrading from the token endpoint

Releases before 1.2.0 took events on the API port with a bearer token (integrations.falco.existingSecret), which only a forwarder that can set a header, such as Falcosidekick, could use. That path is gone: the API port no longer serves POST /api/v1/integrations/falco, the token is no longer read, and integrations.falco.minPriority is no longer read either. Events stop arriving on upgrade until Falco is connected as above. Follow steps 1 to 4, point Falco's own http_output at the integrations port, and delete the old token Secret.

Every event is stored

There is no priority floor on this side: what an event leads to is decided by your runtime rules, not by Falco's priority. Falco's own falco.priority is the place to stop traffic you never want kept, because it saves the delivery. What does arrive is kept for runtime.retentionDays, 90 by default, and then removed by an hourly sweep; 0 keeps it. Only events are removed — issue history, audit entries and rule revisions stay.

Priorities

Falco's own ordering, most severe first, and the names are matched case-insensitively:

emergency  alert  critical  error  warning  notice  informational  debug

A rule can compare against it with >=, = or in. An event whose priority this version does not recognise is stored and matches no priority condition.

Response codes

CodeMeaning
202Stored.
204Accepted and not stored: already on record.
400Not a Falco event, or missing rule, priority or time.
401The client certificate is from the Falco CA but its CN is not falco.
413The body is larger than 64 KiB.
500The event could not be written. Falco logs the failed delivery.

A connection with no client certificate, or one from another CA, never gets as far as a status code: the TLS handshake is refused.

Falco logs any non-2xx as a failed delivery, which is why a duplicate answers 204 rather than a 4xx: it is not the sender's mistake.

Redelivery is safe. Nothing in Falco's payload identifies a delivery, so the operator keys on the detector source, the rule, the event's own timestamp, the container id and the pod. The same detection delivered twice is one row and a 204.

Runtime rules: what happens after an event

Each stored event is checked against your runtime rules, in order, and the first rule that matches decides. No match means record: the event is kept and nothing is sent. The rules are written in the console's Falco section, stored in the database and versioned: every change writes the whole rule set, with its hash, as a revision, and an audit entry saying what changed.

A rule has three parts. Match — every condition that is set must hold:

ConditionMatches
Falco rulesFalco's rule name, exact, any of the list.
TagsFalco's tags, anyOf or allOf the list.
Priority>=, = or in, by Falco's ordering.
SourceFalco's event source (syscall, k8s_audit, ...).
Field conditionsAn output field (fd.name, proc.cmdline, ...) with =, !=, in, contains, startswith, >, <. A condition on a field the event does not carry never matches, != included.
Image verdict / signedThe verdict admission last gave the image and whether its signature verified. An image this installation has never seen matches no image condition.
Namespacesin and/or not_in a list.

A rule with no condition is refused.

Window — count events within duration, counted per image digest (per namespace and pod for an event with no digest), the current one included. The action fires on the event that reaches the count; the events before it are recorded against the rule with action record.

Action — one of:

  • allow — keep the event, do nothing else. Put one at the top to quiet a known-noisy source instead of editing Falco's rule files.
  • record — keep the event.
  • notify — send it to every notification channel subscribed to the runtime_alert event when notify is on, and open an issue in the tracker channels subscribed to it when issue is on. At most one message per rule and image per throttle, an hour by default; a held-back event is counted as dropped_total{reason="throttled"}. A channel receives runtime_alert only once you tick it.
  • block — everything notify does, always with an issue, and it opens a runtime block on the image when the window is reached. block_until says what ends it: triage, the default, where a person releases it, or window, where it also ends once the window passes with no further event.

Every event records the rule that matched and the action on its row, so the events page and the evidence say what was decided, not only what arrived.

The message is titled Runtime alert: <Falco rule>, carries Falco's output line as its body, and lists rule, priority, source, namespace, pod, container, image, digest, node, time, the matched rule and its action. Emergency, alert and critical are sent at level critical; everything else at warning.

Issues are opened only for an event filed against an image digest: one per digest and Falco rule, titled RUNTIME: <rule> in <image> and labelled runtime. The channel's daily cap counts them. An issue closes for one of three reasons, and the closing comment says which:

  • quiet — no event of that rule on that image for 7 days;
  • image_retired — no pod has run that image digest for 24 hours;
  • released — its runtime block was released by triage.

None of them is a fix: the behaviour was reported, not removed. See issue trackers for the channel itself.

Runtime blocks

A block rule whose window is reached on an image digest opens one block for that digest and rule. Further events of the same rule on the same digest count on the open block rather than opening another. An event with no image digest never opens a block: there is nothing admission could recognise it by.

Enforcement. After the break-glass, registry, tag, digest and quota gates and before the vulnerability evaluation, admission asks whether the image's digest has an open block:

  • Under a policy with runtime.enforceBlocks: true the pod is refused with 
    runtime: <rule name>: <Falco rule> x<count> since <first event, RFC 3339>; triage required
    counted as attestkeep_admission_denials_total{reason="runtime"} and attestkeep_runtime_admissions_denied_total. Audit-mode policies record the refusal and admit, as for every other gate.
  • Otherwise the pod is decided as before and its ledger row carries the warning runtime block open (not enforced): <rule name>.
spec:
  runtime:
    enforceBlocks: true

runtime.enforceBlocks is a policy field, default false, also in the console's policy form as "Enforce runtime blocks". An event never stops a running pod: a block acts at the door, on new pods of the digest. A what-if replay reports denied_by_runtime — how many replayed admissions the draft would refuse because of a block open now.

Ending a block. A block is released for one of five reasons:

ReasonBy
triage_false_positive, triage_accepted, triage_resolvedAn admin, in the console's Falco > Blocks page or with the API; a note is required. Written to the audit log.
window_expiredThe hourly sweep, for a block_until: window block whose window passed with no further event of the rule on the digest.
image_retiredThe same sweep, once reconciliation has run within the last day and the image has not been seen running for a day.
 
POST /api/v1/runtime/blocks/{id}/release
{"reason": "triage_false_positive", "note": "..."}

A bad reason or an empty note answers 400, an unknown block 404, one already released 409. A triage release closes the block's runtime issue in the tracker as released, with a comment carrying the reason, the note and who released it. For a block released as a false positive the Blocks page offers Make an allow rule: the rule form opens prefilled with the Falco rule, the namespace and the parent process of the block's latest event, action allow, and the saved rule is moved to the top so it is checked first.

What you get

In the console. The Falco section lists events with the rule that matched and its action, the rules, and the blocks. The images list grows a Runtime column with each image's alert count for the last seven days — only once the operator has actually been sent an event, so an installation that does not use this sees no new column. The image detail panel lists the last 20 alerts for that image: time, priority, rule, namespace and pod, and Falco's own output line.

In the evidence pack. A runtime section carrying:

  • the rule set in force and its revision hash;
  • audit_entries — every rule change, triage release and integration change in the period, each with its kind;
  • matches by rule and action, and the decisions taken, each with the tracker issue it opened, up to 500;
  • the blocks opened or released in the period, and how many admissions runtime refused;
  • coverage: whether the integration is on, the last event and the longest silence in the period.

Two clocks are kept apart. Each decision carries event_time, Falco's own timestamp and the one to argue from, and received_at, when it reached the operator. A block's first_event_at and last_event_at are on Falco's clock, its opened_at and released_at on the operator's. Coverage is about the feed reaching the operator, so its last event and silence are on received_at, and coverage.clock says so. The PDF's column headings name the clock of each time column. The silence is measured from the later of the period start and the first event this installation ever received, because before the first event there was no feed to fall silent.

Ticking the raw events box in the Generate dialog — include_runtime_raw: true on POST /api/v1/evidence — adds the stored events themselves, with the same two clocks, up to 5000. Off by default.

The runtime-observed attestation is met only when the feed is configured and delivered something inside the period — a configured feed that stayed silent for a whole period reports partial, because from inside the operator a detector with nothing to say and a detector that stopped are the same silence. The rest of the package is described on compliance frameworks.

In the metrics.

attestkeep_runtime_events_total{source, priority}
attestkeep_runtime_events_dropped_total{reason="duplicate|unresolved_image|throttled"}
attestkeep_runtime_alerts_notified_total
attestkeep_runtime_rule_matches_total{rule, action}
attestkeep_runtime_blocks_open
attestkeep_runtime_admissions_denied_total

unresolved_image is not a lost event. Falco watches the host as well as the containers on it, and an alert about a process in no container is stored unattributed — it appears in the evidence pack's runtime section with no image beside it.

How an event finds its image

An event names the image the way the runtime pulled it — nginx:1.27 — while this operator records the canonical name docker.io/library/nginx. The endpoint normalises to the second before it stores anything, using the same code path admission uses, so the two match. If the event carries no image digest, the digest of whatever the cluster last admitted under that name and tag is filled in; when there is nothing to fill in, it is left empty rather than guessed.
