Upgrade

A Helm upgrade. Migrations are compiled into the binary and applied on first connection, so there is no separate step to forget.

Upgrading

helm upgrade attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  --namespace attestkeep --wait

Pin the version if your change process needs it:

helm upgrade attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  --namespace attestkeep --version 0.3.5 --wait

What happens to the database

Each migration is recorded when it runs, so it runs exactly once no matter how many replicas start at the same time. Findings, decisions, exceptions and evidence survive the upgrade; nothing is rebuilt from scratch.

1.0.2 to 1.1.0

Migrations 0013 to 0020 are applied on the first start of the new version. They move forward only: the database cannot be taken back to a 1.0.2 schema by a Helm rollback, so a return to 1.0.2 is a restore from backup, not a helm rollback.

helm upgrade --reuse-values works across this version. Every value 1.1.0 adds carries a chart default, so an upgrade that keeps your installed values takes those defaults — kev.source pointing at CISA's catalogue, the Falco endpoint off, and the data key generated rather than supplied.

Three things appear on the upgrade itself:

  • The chart generates a <release>-data-key Secret and preserves it from then on. Add it to your backup set. It encrypts the issue-tracker credentials this installation stores, and a credential sealed under a key you no longer hold cannot be opened: each tracker channel then needs its token entered again. See Backup and restore.
  • Tracker channels configured before 1.1.0 hold their token in plain text. One pass on the first start, on the leader, seals them in place and logs how many it changed. There is nothing to run by hand.
  • The ClusterRole gains read access to Services and Ingresses, which is what the exposed signal reads. An installation that manages its own RBAC has to grant the two rules itself; an operator that cannot list them derives exposure from the pod spec alone, logs a warning and admits.

Nothing about an installed policy, licence or evidence document changes. Existing policies behave as before: the two new gates that have a default, endOfLifeOS and knownExploited, default to warn, and the provenance, VEX and deployment-context blocks are off until you write them.

What happens to admission during the rollout

With the default two replicas, one keeps answering while the other is replaced. With failurePolicy: Ignore a moment with no replica means unreviewed rather than blocked; with Fail it means deployments wait. That is the same trade described in Admission, and an upgrade is exactly when it becomes visible.

Verifying what you are about to run

Every release is signed. Check it before you upgrade:

cosign verify ghcr.io/attestkeep/attestkeep-k8s:0.3.5 \
  --certificate-identity-regexp '^https://github.com/attestkeep/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

A product that checks your signatures should be checkable the same way. The chart is signed too, and the release page carries the digest for each artefact.

Rolling back

helm rollback attestkeep --namespace attestkeep

Rolling back the chart does not roll back the schema. Migrations move forward only, and no rollback of the database is offered. A rollback across a release that changed the schema — 1.0.2 to 1.1.0 is one, and the release notes say when a release is another — is a restore-from-backup exercise, not a Helm command. Backup and restore is the page that exercise assumes you have read before you needed it.
