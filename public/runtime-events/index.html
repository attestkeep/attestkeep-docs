Runtime events from Falco

Falco watches what containers do after they start. Attestkeep can receive Falco's events, store each one against the image and pod that raised it, and act on it through runtime policies you write in the console.

Attestkeep does not ship, install, configure or write to Falco. Detection is done by your Falco and its rules. Attestkeep only receives the events. A runtime event never changes an admission decision. See what Attestkeep does not do.

How it works

  1. A Falco rule fires on a node, for example because someone opened a shell in a container.
  2. The event is sent as JSON to the operator's integrations port over mutual TLS. Falco sends it itself from http_output, or Falcosidekick forwards it from its webhook output. Either way the sender presents a client certificate that the operator issued.
  3. The operator stores the event and ties it to the image and digest the container runs.
  4. Your runtime policies are checked in order. The first one that matches decides what happens: keep a record, send a notification, open an issue in your tracker, stop the pod.
  5. The event and the decision show up under Falco > Events, next to the image in the images list, and in the evidence pack.

Example

An admin creates a policy under Falco > Policies > New policy:

  • Name: Stop shells in shop
  • Falco rules: Terminal shell in container
  • Only in namespaces: shop
  • Send a notification, Open an issue and Stop the pod on, with Kill at once
  • State on. A new policy starts off.

Saving asks once more, because the policy deletes pods. Later someone runs:

kubectl -n shop exec -it deploy/web -- sh

Falco's upstream rule Terminal shell in container (priority Notice, source syscall) fires for the interactive shell. The event reaches the operator, which stores it and matches the policy. Then:

  • The pod is evicted with a one-second grace period. The shell ends with it, and the Deployment starts a new pod.
  • The audit log gets a runtime_pod_stop entry with policy:Stop shells in shop as the actor.
  • Channels subscribed to Runtime alert get a message titled Runtime alert: Terminal shell in container, which says the policy stopped the pod.
  • If the event could be tied to an image digest, a tracker channel opens an issue titled RUNTIME: Terminal shell in container in <image>.
  • Falco > Events lists the event with the policy name and action Notify.

Requirements

  • Falco installed with the upstream falcosecurity/falco Helm chart. The values on this page are for chart 9.2.0 (Falco 0.45.0, Falcosidekick 2.32.0). Older versions have not been checked.
  • falco.json_output: true. The operator reads Falco's JSON event.
  • Network access from the Falco pods, or the Falcosidekick pods, to the operator's Service on the integrations port, 8444 by default. Usually both run in the same cluster and this is a ClusterIP Service, so no ingress is needed.
  • An admin account in the console. Only admins can see the integration page, download certificates and edit policies.
  • For a policy that stops pods: rbac.allowEnforce: true in the Attestkeep chart.
  • For messages and issues: a notification channel, or a GitHub, GitLab or Jira channel (see issue trackers), subscribed to Runtime alert.

Direct or through Falcosidekick

The Attestkeep chart value integrations.falco.connection picks one of two ways in:

  • mtls (default): Falco posts each event from its own http_output straight to the operator.
  • sidekick: use this if your Falco already sends to Falcosidekick. Falco's http_output takes one URL only, and the Falco chart points it at Sidekick. Sidekick's webhook output then forwards to the operator.

The listener and the client certificate are the same in both cases. The setting decides which Falco chart values the console and the install notes show you. Any value other than mtls or sidekick makes the chart fail.

How the connection is authenticated

Falco's http_output cannot add a header, so there is no token. The only credential is a client certificate.

  • When the integration is on, the operator creates its own small CA (CN=attestkeep-falco-ca, ECDSA P-256, valid five years) and one client certificate (CN=falco, client authentication only, valid one year). Both are kept in the Secret <release>-falco-mtls in the operator's namespace.
  • The integrations port serves one route, POST /api/v1/integrations/falco. The TLS handshake requires a client certificate signed by that CA, and the handler also requires the CN to be falco. The API port does not serve this route.
  • The server certificate is the one the admission webhook already uses. It is issued for the Service name <release>.<namespace>.svc. Falco verifies it with the ca.crt from the bundle you download.

Setup

1. Turn the integration on

In the Attestkeep chart values:

integrations:
  port: 8444
  falco:
    enabled: true
    connection: mtls   # or sidekick
helm upgrade attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  -n attestkeep -f values.yaml

The chart opens the integrations port on the pod and the Service. The operator creates the Secret when it starts. After the upgrade, helm prints the Falco chart values for the connection you chose.

With enabled: false, the default, there is no listener and no CA. The Falco menu then shows only Falco integration, and only to admins.

2. Download the certificates

Open Falco > Falco integration. The page shows the status, the connection, the endpoint URL, when the client certificate expires and when the last event arrived. It also shows the commands and Helm values for the next two steps, with your endpoint filled in.

Download certificates saves attestkeep-falco-mtls.tar.gz with three files:

FileWhat it is
ca.crtThe CA of the operator's server certificate. Falco uses it to verify the operator.
client.crtThe client certificate Falco presents.
client.keyIts private key. Anyone holding it can post events that your policies act on, so treat it as a secret.

The same bundle is available from GET /api/v1/integrations/falco/bundle (admin). Every download is written to the audit log as runtime_integration_change.

3. Create the Secret in the Falco namespace

tar xzf attestkeep-falco-mtls.tar.gz
kubectl -n falco create secret generic attestkeep-falco-client \
  --from-file=ca.crt --from-file=client.crt --from-file=client.key

If Falco runs in another namespace, change -n falco. With connection: sidekick the Secret has to be in the namespace where Sidekick runs, which is the Falco release namespace when Sidekick comes from the Falco chart.

4a. Falco values for connection: mtls

# values for the falcosecurity/falco chart
falco:
  json_output: true
  http_output:
    enabled: true
    url: https://attestkeep.attestkeep.svc:8444/api/v1/integrations/falco
    mtls: true
    ca_cert: /etc/falco/certs/client/ca.crt
    client_cert: /etc/falco/certs/client/client.crt
    client_key: /etc/falco/certs/client/client.key
certs:
  existingClientSecret: attestkeep-falco-client
  • The URL is https://<release>.<namespace>.svc:<integrations.port>/api/v1/integrations/falco. The integration page shows yours.
  • certs.existingClientSecret is the Falco chart's value for a Secret holding client.crt, client.key and ca.crt for http_output mTLS. The chart mounts it at /etc/falco/certs/client, which is where the paths above point.

4b. Falco values for connection: sidekick

Use these instead of the http_output values in 4a.

# values for the falcosecurity/falco chart
falco:
  json_output: true
falcosidekick:
  enabled: true
  config:
    mutualtlsclient:
      certfile: /etc/attestkeep/falco-client/client.crt
      keyfile: /etc/attestkeep/falco-client/client.key
      cacertfile: /etc/attestkeep/falco-client/ca.crt
    webhook:
      address: https://attestkeep.attestkeep.svc:8444/api/v1/integrations/falco
      mutualtls: true
      minimumpriority: ""
  extraVolumes:
    - name: attestkeep-falco-client
      secret:
        secretName: attestkeep-falco-client
  extraVolumeMounts:
    - name: attestkeep-falco-client
      mountPath: /etc/attestkeep/falco-client
      readOnly: true
  • With falcosidekick.enabled: true, the Falco chart turns on http_output and points it at the Sidekick Service, but only while falco.http_output.url is empty. If you are switching from 4a, set falco.http_output.url back to "" and falco.http_output.mtls to false. Otherwise Falco keeps posting to the operator directly.
  • The webhook output uses the same client certificate, mounted from the same Secret. Sidekick's other outputs are not affected.
  • minimumpriority: "" forwards events of every priority. If you set a priority there, Sidekick drops lower ones before they reach Attestkeep.
  • Sidekick does not always forward the event unchanged. If the JSON is longer than 4096 bytes, it cuts every output_fields string longer than 512 bytes to 507 and appends [...]. If you use its customtags, customfields or outputFieldFormat settings, the stored tags, fields and output line include those changes.

5. Check that events arrive

Apply the Falco values with helm upgrade on your Falco release, then trigger a rule. An interactive shell is the simplest:

kubectl -n <namespace> exec -it <pod> -- sh

Without -t there is no terminal and Terminal shell in container does not fire.

Then look at Falco > Falco integration > Last event. Next to it the page says whether the event came from Falco or from Falcosidekick. If that does not match integrations.falco.connection, the page shows a warning, because the values it gives you are not the ones your Falco is using.

Policies, Rules and Events appear in the Falco menu once the integration is on. Each of them starts with a status line, either "Falco connected · last event <time>" or the reason it is not connected.

The same check through the API is GET /api/v1/runtime/status, which returns enabled, last_event_at, events_24h and by_source.

Runtime policies

Every stored event is checked against the policies on Falco > Policies, top to bottom. The first enabled policy that matches decides. If none matches, the event is kept with action record and nothing is sent. Use the arrows on the page to change the order.

A policy change reaches the replica that saved it at once. Other operator replicas pick it up within 15 seconds.

The policy form

FieldWhat it does
NameRequired, at most 128 characters, unique.
Falco rulesThe policy matches an event from any of these rules, by exact name. Pick from the Rules list or type the name of your own rule. At least one is required.
All namespaces / Only in namespacesLimits the policy to events from pods in the listed namespaces.
Send a notificationSends the event to every enabled channel subscribed to Runtime alert.
Open an issueOpens an issue through the tracker channels subscribed to Runtime alert.
Stop the podEvicts the pod the event came from. Kill at once or Use the application's shutdown time. See stopping the pod.
StateOn or Off. A new policy is Off until you switch it on. An Off policy is kept and does nothing.

With any of the three actions on, the policy is saved with action notify. With all three off it is saved as record: matching events are recorded against the policy and nothing else happens.

Notifications and issues

A message is titled Runtime alert: <Falco rule>. Its body is Falco's output line. It also lists the rule, priority, source, namespace, pod, container, image, digest, node, time, the policy and its action. If the policy stopped the pod, the message says so. Events with priority emergency, alert or critical are sent at level critical, everything else at warning.

A policy sends at most one message per image digest per hour. For an event with no digest the limit is per namespace and pod. Events held back this way are counted in attestkeep_runtime_events_dropped_total{reason="throttled"}. The limit applies to messages and issues. It does not delay stopping a pod.

An issue is opened only when the event is tied to an image digest. There is one issue per digest and Falco rule. It is titled RUNTIME: <rule> in <image>, carries the label runtime and counts toward the channel's daily cap. It closes by itself as quiet when the rule has not fired on that image for 7 days, or as image_retired when no running pod has used that digest for 24 hours. The closing comment gives the reason. Neither reason means the problem was fixed. See issue trackers for setting up the channel.

An event counts as notified only if at least one enabled channel is subscribed to receive it. With no such channel nothing is sent, and the evidence pack does not count the alert as sent. When you add a channel in the console, Runtime alert is switched on by default.

Conditions available through the API

The API (/api/v1/runtime/rules, admin for writes) accepts more than the form shows. A policy saved with any of these keeps them when it is edited in the console, and the form shows a notice that the policy has settings it does not display.

FieldMeaning
match.rulesFalco rule names, exact, any of the list. This is the form's Falco rules field.
match.tagsFalco tags, with mode anyOf or allOf.
match.priorityop >= or = with value, or in with values, in Falco's priority order.
match.sourceFalco's event source, exact, for example syscall.
match.fieldsConditions on output_fields, for example proc.cmdline, with =, !=, in, contains, startswith, >, <. A condition on a field the event does not carry never matches, != included.
match.imagecompliance (Compliant, NonCompliant, Unknown) is the verdict admission last gave the image. signed is whether its signature verified. An image Attestkeep has never seen matches no image condition.
match.namespacesin and not_in lists.
windowcount events within duration before the action fires, counted per image digest (per namespace and pod without a digest), the current event included. Earlier events in the window are recorded against the policy with action record. The form saves 1 event in 1h, which fires on the first event.
action.kindallow, record or notify. allow keeps the event and does nothing else. Placed first, it quiets a noisy source without changing Falco's rules.
action.notify, action.issue, action.stop, action.stop_modeThe form's switches. Allowed only with notify. stop_mode is immediate (default) or graceful.
action.throttleThe message limit per image. One hour if not set.
noteFree text, stored with the policy and its revisions.

A policy with no condition is refused with 400, and a name already in use with 409. The action block was removed in 1.3.1 and is refused. Existing block policies were changed to notify with issue on.

What is recorded

Each event row carries the policy that matched and the action taken. The policy's name, the hash of its content and the hash of the whole policy set are stored with the decision, so renaming or deleting the policy later does not change what past events show. Every policy change stores the whole set with its hash as a revision and writes an audit entry of kind runtime_rule_change.

Stopping the pod

A policy with Stop the pod on stops the pod named in the event as soon as the event arrives, or as soon as the window is reached if the policy has one. The operator asks the API server to evict the pod, so PodDisruptionBudgets apply. If a budget does not allow the eviction, the pod keeps running and the audit log records why.

  • Kill at once (stop_mode: immediate, default): the eviction uses a one-second grace period. The containers get SIGTERM and are killed a second later. Anything started inside them, an open shell included, ends there.
  • Use the application's shutdown time (stop_mode: graceful): the pod gets its own termination grace period, 30 seconds unless the pod sets another. A shell opened inside keeps running until then.

The pod's controller starts a new pod. A pod without a controller is gone for good. If the cause is in the image, the new pod can trigger the same event and be stopped again.

  • Stopping needs rbac.allowEnforce: true in the Attestkeep chart, which grants pod eviction. Without it the attempt is refused and recorded.
  • Pods in the operator's own namespace are never stopped. No other namespace is excluded, so use Only in namespaces to keep a stop policy away from system namespaces.
  • An event must name the pod (k8s.ns.name and k8s.pod.name in output_fields). With the Falco chart's defaults these fields are present.
  • A pod that is already terminating is left alone. Each operator replica asks to stop a given pod at most once every 10 minutes, so one shell session does not cause a series of evictions.

Every attempt is written to the audit log as runtime_pod_stop. The actor is policy:<name> and the target is the pod. The detail holds the Falco rule, pod UID, container, image, digest, node, event id and result. Stopping a pod does not change admission: new pods of the same image are admitted as before.

Writing Falco rules in the console

Falco > Rules > New rule (admins) opens an editor for a Falco rules file: rules, macros, lists and overrides in Falco's own YAML, saved under a file name. The editor is in beta.

Completion and checks follow the Falco version running in your cluster. The editor finds Falco by the label the Falco chart sets, app.kubernetes.io/name=falco, in any namespace. If no running pod has that label, you can still write rules but not validate them.

  • Validate with Falco starts a one-off pod in the operator's namespace with the same image your Falco runs. It loads Falco's default rules and then your file, runs falco in validation mode, and is deleted once the result is read. The pod has no service-account token, runs as non-root with a read-only filesystem and all capabilities dropped. Your running Falco is not touched. The chart creates the Role this needs, <release>-rule-validation.
  • Save is enabled only after Falco has accepted exactly the text in the editor, and the server validates it again before storing it. Each save is a new version, recorded with who saved it and which Falco image and version accepted it. The rules in the file appear in the Rules list, so a policy can use them before any event arrives. A rule name that another saved file already defines is refused with 409.
  • Publish pushes a saved version to your OCI registry as a falcoctl rulesfile artifact, tagged with the version number and with latest. Enter the repository (registry and path, no tag). If the registry needs a login, enter the name of a kubernetes.io/dockerconfigjson Secret in the operator's namespace. Attestkeep reads the Secret when it pushes and does not store the credential. A registry listed in scan.insecureRegistries is reached over plain HTTP. If your Falco image has changed since the version was validated, publishing validates it again first.

Your Falco loads the file through falcoctl. Add the reference to the falcoctl values of your Falco chart and add the file to rules_files after Falco's own rules. The editor shows these values with your repository and file name filled in:

# values for the falcosecurity/falco chart
falcoctl:
  config:
    artifact:
      install:
        refs:
          - falco-rules:5
          - registry.example.com/falco/my-rules:latest
      follow:
        refs:
          - falco-rules:5
          - registry.example.com/falco/my-rules:latest
        every: 5m
falco:
  rules_files:
    - /etc/falco/falco_rules.yaml
    - /etc/falco/my-rules.yaml
  • falco-rules:5 is the Falco chart's default reference. Helm replaces a list instead of merging it, so keep it and any other references you already have. Without it, /etc/falco/falco_rules.yaml is not installed.
  • falcoctl checks the reference every follow.every. The chart's default is 168h.
  • If the registry needs a login, falcoctl reads it from FALCOCTL_REGISTRY_AUTH_BASIC (registry,user,password), set in both falcoctl.artifact.install.env and falcoctl.artifact.follow.env.
  • Deleting a file in the console removes its rules from the Rules list. What was already published stays in the registry and in every Falco that installed it until you remove the reference from falcoctl.

Validating, saving, deleting and publishing are written to the audit log as falco_rule_validate, falco_rule_file_change and falco_rule_file_publish.

Where events show up

Console

  • Falco > Events lists events with the policy that matched and its action. Filters: free text (rule, pod, container, output), priority, what the policy was set to do (Allow, Record, Notify, Open an issue, Stop the pod), Falco rule, tag, namespace, pod and policy, over a time range. Results are shown a page at a time. The detail view shows Falco's output, tags, output fields and whether a message was sent.
  • Falco > Rules lists the Falco rules the operator knows: the 25 stable rules from falcosecurity/rules that ship with it, the rules from your saved files, and rule names seen in events.
  • The images list gets a Runtime column with each image's event count for the last 7 days and a link to an open runtime issue. The column appears only after the operator has stored at least one event.
  • An image's detail panel lists its last 20 events: time, priority, rule, namespace and pod, and Falco's output line.

Evidence pack

The runtime section contains:

  • The event count by priority, the busiest Falco rules, alerts sent, and runtime issues opened and closed
  • The policy set in force when the pack was generated, with its revision hash
  • audit_entries: policy changes, pods stopped and integration changes in the period, each with its kind
  • Match counts by policy and action
  • decisions: events a policy acted on (action notify), each with the issue it opened, up to 500
  • coverage: whether the integration is on, the last event, and the longest gap without events in the period

Two timestamps are kept apart. event_time is Falco's own timestamp. received_at is when the operator received the event. Coverage measures whether the feed reached the operator, so it uses received_at, and coverage.clock says so. In the PDF, the decisions and raw events tables name the clock in each time column heading. The longest gap is measured from the start of the period or from the first event this installation ever received, whichever is later.

Include raw runtime events in the Generate dialog (include_runtime_raw: true on POST /api/v1/evidence) adds the stored events themselves, up to 5000. It is off by default.

The runtime-observed attestation is met when the integration is on and at least one event arrived in the period. It is partial when the integration is on and no event arrived, because a quiet cluster and a Falco that stopped sending look the same from the operator's side. It is a gap when the integration is off. See compliance frameworks for the rest of the pack.

Metrics

attestkeep_runtime_events_total{source, priority}
attestkeep_runtime_events_dropped_total{reason="duplicate|unresolved_image|throttled"}
attestkeep_runtime_alerts_notified_total
attestkeep_runtime_rule_matches_total{rule, action}

In attestkeep_runtime_rule_matches_total, rule is the runtime policy's name. unresolved_image does not mean the event was lost. Falco also watches processes on the host, outside any container. Such an event is stored without an image and appears in the evidence pack without one.

Reference

Priorities

Falco's order, most severe first. Names are matched without regard to case, and info is read as informational.

emergency  alert  critical  error  warning  notice  informational  debug

An event with a priority outside this list is stored and matches no priority condition.

Every event is stored

Attestkeep has no priority threshold of its own. Your policies decide what an event leads to, not its priority. To stop Falco sending events you never want to keep, set Falco's own falco.priority. That saves the delivery as well.

Retention

Stored events are kept for runtime.retentionDays days, 90 by default, and removed by an hourly job. 0 keeps them indefinitely. Only events are removed. Issue history, audit entries and policy revisions are kept.

Response codes

CodeMeaning
202Stored. The policy decision is written before this is returned.
204Accepted but not stored, because the same event is already on record.
400The body is not a Falco event, the Content-Type is not JSON, or rule, priority or time is missing.
401The client certificate is from the Falco CA but its CN is not falco.
413The body is larger than 64 KiB.
500The event could not be written. The sender logs a failed delivery.

A connection without a client certificate, or with one from another CA, gets no status code. The TLS handshake fails.

Falco logs every non-2xx answer as a failed delivery. A duplicate is not the sender's fault, so it gets 204, not a 4xx.

Delivering the same event twice is safe. Falco's payload has no delivery id, and Sidekick's uuid is new on every send, so the operator identifies an event by its source, rule, Falco timestamp, container id and pod. The second copy is answered with 204 and not stored.

How an event is tied to an image

The operator reads the image from container.image.repository, container.image.tag and container.image.digest in output_fields. Falco reports the image as the runtime pulled it, for example nginx:1.27. Attestkeep stores images by canonical name, here docker.io/library/nginx, so the event's name is normalised with the same code admission uses before it is stored.

If the event has no digest, the operator uses the digest it most recently recorded for that name and tag. If it has none, the digest stays empty. Without a digest the event still triggers messages and pod stops, but no issue.

Rotating the client certificate

Rotate on Falco > Falco integration, or POST /api/v1/integrations/falco/rotate (admin, audited as runtime_integration_change), issues a new client certificate from the same CA. The old certificate is not revoked and works until it expires, so events keep arriving while you switch.

Download the bundle again, replace the Secret and restart the pods that mount it so they load the new files:

tar xzf attestkeep-falco-mtls.tar.gz
kubectl -n falco create secret generic attestkeep-falco-client \
  --from-file=ca.crt --from-file=client.crt --from-file=client.key \
  --dry-run=client -o yaml | kubectl apply -f -

# connection: mtls
kubectl -n falco rollout restart daemonset/falco
# connection: sidekick
kubectl -n falco rollout restart deployment/falco-falcosidekick

The workload names above are the ones the Falco chart creates for a release named falco. The client certificate is valid for one year. The integration page shows its expiry date, and after it expires the Falco pages say Falco is not connected. Rotating the Falco CA itself is not offered in this version.

When the operator's server certificate rotates

The ca.crt in the bundle is the CA of the operator's server certificate, which is renewed about once a year. The bundle contains the current CA and, while it is still valid, the previous one. Falco therefore keeps connecting through one renewal but not through a second.

Once the CA has changed since the bundle was last downloaded, Falco > Falco integration shows "Certificates changed on <date>". Download the bundle again and replace the Secret as above before the next renewal.

Upgrading from the token endpoint

Releases before 1.2.0 accepted events on the API port with a bearer token (integrations.falco.existingSecret). That is gone. The API port no longer serves POST /api/v1/integrations/falco, and neither the token nor integrations.falco.minPriority is read. Events stop arriving after the upgrade until Falco is connected as described above. Follow steps 1 to 4, then delete the old token Secret.
