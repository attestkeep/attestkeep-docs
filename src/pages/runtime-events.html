Runtime events from Falco

Attestkeep decides what may run. Falco watches what a container does once it is running. This integration is the join between them: your Falco's events arrive here, are filed against the image that produced them, and your runtime policies decide what each one leads to.

Attestkeep does not ship, install or run Falco, and never writes to it. The detection is yours; this is a place to put what it found and decide what follows. An event never changes an admission decision. What it leads to is up to your runtime policies: a message, an issue and, only where a policy says so, stopping the pod it came from. A broken alert stream cannot break your cluster: no events means nothing is done. Runtime behaviour detection stays outside what this product does, for the reasons on what Attestkeep does not do.

What you need

  • Falco, installed however you install it. Written against Falco 0.45 and the upstream falcosecurity/falco Helm chart; older versions are not claimed.
  • Network reach from the Falco pods to the operator's Service on the integrations port, 8444 by default. Both usually live in the same cluster, so this is a ClusterIP address and no ingress.

Two ways in, chosen with integrations.falco.connection. With mtls, the default, Falco sends each event itself, from its own http_output, straight to the operator. If your Falco already feeds Falcosidekick, use sidekick: Falco's http_output has a single URL and the Falco chart points it at Sidekick, so the events reach the operator through Sidekick's webhook output (step 4b). Either way the listener and the client certificate are the same, and there is no token.

How Falco proves who it is

Falco's http_output cannot send a header, so there is no token. It can present a client certificate, and that is the whole of the authentication:

  • With the integration on, the operator creates a small CA of its own (CN=attestkeep-falco-ca, ECDSA P-256, five years) and one client certificate for Falco (CN=falco, client authentication only, one year), in the Secret <release>-falco-mtls in the operator's namespace.
  • The operator serves POST /api/v1/integrations/falco on its own TLS port, the integrations port, and nothing else there. The handshake requires a client certificate signed by that CA, and the endpoint then requires its CN to be falco. The API port does not serve this route at all.
  • The server side is the operator's existing serving certificate, the one the admission webhook uses, whose name is the Service, <release>.<namespace>.svc. Falco verifies it with the ca.crt from the bundle.

1. Turn the integration on

integrations:
  port: 8444
  falco:
    enabled: true
    connection: mtls   # or sidekick, see 4b
helm upgrade attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  -n attestkeep -f values.yaml

The chart opens the integrations port on the pod and the Service, and the operator creates the Secret on start. Any other value of connection fails the chart. With enabled: false, the default, there is no listener and no CA; the console's Falco menu then shows admins only Falco integration, and shows nothing to other roles. After an upgrade, helm prints the Falco chart values for the chosen connection.

2. Download the certificates

In the console, Falco > Falco integration (admins only) shows the connection, the endpoint URL, when Falco's client certificate expires and when the last event arrived. Download certificates gives attestkeep-falco-mtls.tar.gz with three files:

FileWhat it is
ca.crtThe CA that verifies the operator's serving certificate.
client.crtFalco's client certificate.
client.keyIts private key. Keep it private: whoever holds it can post events your runtime policies act on.

The same bundle is GET /api/v1/integrations/falco/bundle (admin). Every download is written to the audit log.

3. Put them in the Falco namespace

tar xzf attestkeep-falco-mtls.tar.gz
kubectl -n falco create secret generic attestkeep-falco-client \
  --from-file=ca.crt --from-file=client.crt --from-file=client.key

4. Point Falco at the operator (connection: mtls)

Values for the upstream falcosecurity/falco chart. certs.existingClientSecret is that chart's own value for an existing Secret holding client.crt, client.key and ca.crt for outbound HTTP output mTLS, and the paths are the ones its README uses for it:

# values for the falcosecurity/falco chart
falco:
  json_output: true
  http_output:
    enabled: true
    url: https://attestkeep.attestkeep.svc:8444/api/v1/integrations/falco
    mtls: true
    ca_cert: /etc/falco/certs/client/ca.crt
    client_cert: /etc/falco/certs/client/client.crt
    client_key: /etc/falco/certs/client/client.key
certs:
  existingClientSecret: attestkeep-falco-client

The URL is the one the console shows: https://<release>.<namespace>.svc:<integrations.port>/api/v1/integrations/falco. json_output: true is required — the endpoint reads Falco's JSON alert.

4b. Through Falcosidekick (connection: sidekick)

Use these Falco chart values instead of the http_output ones above. The chart then points Falco's http_output at Falcosidekick, and Sidekick's webhook output posts to the operator with the same client certificate, mounted from the same Secret. Sidekick's other outputs keep working.

# values for the falcosecurity/falco chart
falco:
  json_output: true
falcosidekick:
  enabled: true
  config:
    mutualtlsclient:
      certfile: /etc/attestkeep/falco-client/client.crt
      keyfile: /etc/attestkeep/falco-client/client.key
      cacertfile: /etc/attestkeep/falco-client/ca.crt
    webhook:
      address: https://attestkeep.attestkeep.svc:8444/api/v1/integrations/falco
      mutualtls: true
      minimumpriority: ""
  extraVolumes:
    - name: attestkeep-falco-client
      secret:
        secretName: attestkeep-falco-client
  extraVolumeMounts:
    - name: attestkeep-falco-client
      mountPath: /etc/attestkeep/falco-client
      readOnly: true
  • The Falco chart points http_output at Sidekick only while falco.http_output.url is empty. Coming from connection: mtls, set it back to "" (and mtls: false), or Falco keeps posting to the operator directly.
  • minimumpriority: "" keeps every event, as a direct connection does.
  • The operator records each event as delivered by falcosidekick or falco, and the console says so next to Last event, with a warning when it does not match connection. Sidekick may change what arrives: when an event's JSON is longer than 4096 characters it shortens every output_fields string over 512 characters to 507 plus [...], and its customtags, customfields and outputFieldFormat settings, if you use them, change the tags and the output line.

Tested with the falcosecurity/falco chart 9.2.0 (Falco 0.45.0, Falcosidekick 2.32.0).

5. Check it arrives

Trigger any rule — kubectl exec a shell into a pod, for example — and look at Falco > Falco integration > Last event, or at the line at the top of every Falco page; Policies, Rules and Events appear in the sidebar once the integration is on. GET /api/v1/runtime/status answers the same question: enabled, last_event_at, events_24h.

Rotating the certificates

Rotate on the same page, or POST /api/v1/integrations/falco/rotate (admin, audited), issues a new client certificate from the same CA. The previous one is not revoked: it keeps working until its own expiry, so Falco keeps delivering while you download the new bundle and replace the Secret in the Falco namespace. Rotating the Falco CA itself is not offered in this version.

The ca.crt in the bundle is the CA of the operator's serving certificate, and that pair rotates about once a year. The bundle carries the previous CA as well as the current one, so Falco keeps connecting through one rotation; it does not through the second. As soon as the CA has changed since the bundle was last downloaded, Falco > Falco integration says "Certificates changed on <date>": download the bundle again and replace the Secret in the Falco namespace before the next rotation.

Upgrading from the token endpoint

Releases before 1.2.0 took events on the API port with a bearer token (integrations.falco.existingSecret). That path is gone: the API port no longer serves POST /api/v1/integrations/falco, the token is no longer read, and integrations.falco.minPriority is no longer read either. Events stop arriving on upgrade until Falco is connected as above. Follow steps 1 to 4 (or 4b) and delete the old token Secret.

Every event is stored

There is no priority floor on this side: what an event leads to is decided by your runtime policies, not by Falco's priority. Falco's own falco.priority is the place to stop traffic you never want kept, because it saves the delivery. What does arrive is kept for runtime.retentionDays, 90 by default, and then removed by an hourly sweep; 0 keeps it. Only events are removed — issue history, audit entries and rule revisions stay.

Priorities

Falco's own ordering, most severe first, and the names are matched case-insensitively:

emergency  alert  critical  error  warning  notice  informational  debug

A policy can compare against it with >=, = or in. An event whose priority this version does not recognise is stored and matches no priority condition.

Response codes

CodeMeaning
202Stored.
204Accepted and not stored: already on record.
400Not a Falco event, or missing rule, priority or time.
401The client certificate is from the Falco CA but its CN is not falco.
413The body is larger than 64 KiB.
500The event could not be written. Falco logs the failed delivery.

A connection with no client certificate, or one from another CA, never gets as far as a status code: the TLS handshake is refused.

Falco logs any non-2xx as a failed delivery, which is why a duplicate answers 204 rather than a 4xx: it is not the sender's mistake.

Redelivery is safe. Nothing in Falco's payload identifies a delivery, so the operator keys on the detector source, the rule, the event's own timestamp, the container id and the pod. The same detection delivered twice is one row and a 204.

Runtime policies: what happens after an event

Each stored event is checked against your runtime policies, in order, and the first policy that matches decides. No match means record: the event is kept and nothing is sent. Policies are written in the console's Falco > Policies page, stored in the database and versioned: every change writes the whole set, with its hash, as a revision, and an audit entry saying what changed.

A policy has three parts. Match — every condition that is set must hold:

ConditionMatches
Falco rulesFalco's rule name, exact, any of the list.
TagsFalco's tags, anyOf or allOf the list.
Priority>=, = or in, by Falco's ordering.
SourceFalco's event source (syscall, k8s_audit, ...).
Field conditionsAn output field (fd.name, proc.cmdline, ...) with =, !=, in, contains, startswith, >, <. A condition on a field the event does not carry never matches, != included.
Image verdict / signedThe verdict admission last gave the image and whether its signature verified. An image this installation has never seen matches no image condition.
Namespacesin and/or not_in a list.

A policy with no condition is refused.

Window — count events within duration, counted per image digest (per namespace and pod for an event with no digest), the current one included. The action fires on the event that reaches the count; the events before it are recorded against the policy with action record.

Action — one of:

  • allow — keep the event, do nothing else. Put one at the top to quiet a known-noisy source instead of editing Falco's rule files.
  • record — keep the event.
  • notify — send it to every notification channel subscribed to the runtime_alert event when notify is on, open an issue in the tracker channels subscribed to it when issue is on, and stop the pod when stop is on (below). At most one message per policy and image per throttle, an hour by default; a held-back event is counted as dropped_total{reason="throttled"}.

block was removed in 1.3.1, together with runtime blocks: a policy written as block became notify with issue on, and the API refuses block.

Every event records the policy that matched and the action on its row, so the events page and the evidence say what was decided, not only what arrived. The policy's name, the hash of its content and the hash of the whole set are stored with the decision, so renaming or deleting a policy later does not change what its past events say decided them.

Who receives it. A new notification channel is subscribed to runtime_alert from 1.3.1, so a channel added after the policy gets the alerts the policy was written to send. An event is recorded as notified only when at least one enabled channel receives it; with no channel, nothing is sent and the evidence does not count an alert that reached no one.

The message is titled Runtime alert: <Falco rule>, carries Falco's output line as its body, and lists rule, priority, source, namespace, pod, container, image, digest, node, time, the matched policy and its action. When the policy stopped the pod, the message says so instead of saying the pod is still running. Emergency, alert and critical are sent at level critical; everything else at warning.

Issues are opened only for an event filed against an image digest: one per digest and Falco rule, titled RUNTIME: <rule> in <image> and labelled runtime. The body says whether a runtime policy stopped the pod. The channel's daily cap counts them. An issue closes as quiet (no event of that rule on that image for 7 days) or image_retired (no pod has run that image digest for 24 hours), and the closing comment says which. Neither is a fix: the behaviour was reported, not removed. See issue trackers for the channel itself.

Stopping the pod

A notify policy with stop on stops the pod the event names as soon as the event arrives (once the window, when there is one, is reached). The operator asks the API server to evict it, so a PodDisruptionBudget is honoured: while one does not allow it, the pod keeps running and the audit log says so. The pod's controller starts a fresh one; a pod nothing manages is gone for good, and if the cause is in the image the new pod can raise the event again.

  • stop_mode: immediate, the default, evicts with a one-second grace: the containers are killed within about two seconds, and whatever was started in them, an open shell session included, ends there.
  • stop_mode: graceful gives the pod its own termination grace period, 30 seconds by default, to shut down cleanly; a session opened inside lives until then.

It needs the chart's rbac.allowEnforce: true (pod eviction); without it the attempt is refused and recorded. A pod in the operator's own namespace is never stopped, and one pod is stopped once however many events it raises. Every attempt is written to the audit log as runtime_pod_stop, with the policy as the actor (policy:<name>), the pod as the target, and the pod UID, container, image, digest, node, the event id and the result in the detail. An event never changes an admission decision: a stop acts on the running pod, not on new pods of the image.

Writing Falco rules in the console

Falco > Rules > New rule (admins) opens an editor for a Falco rules file: Falco's own YAML, rules, macros, lists and overrides together, kept under a name. It is in beta in this version. The editor completes and checks as you type for the Falco version your cluster runs, which it reads from the Falco pods (found by the label Falco's own Helm chart sets; a Falco installed some other way is not found, and the editor says so).

  • Validate runs falco --validate on the file in a one-off pod with the very image your Falco runs, in the operator's namespace: no service-account token, no privileges, read-only, deleted as soon as the answer is read. Falco itself is not touched. The chart creates the Role the pod needs, <release>-rule-validation.
  • Save is offered only once the same text has passed Falco, and the server validates it again before it stores anything. Every save is a new version, kept with who saved it and which Falco image and version accepted it. The rules the file defines join the Rules list, so a policy can name them before any event has arrived; a rule another saved file already defines is refused with 409.
  • Publish pushes a saved version to your own OCI registry as falcoctl's rulesfile artifact, tagged with its version number and latest. Give the repository (registry and path, no tag) and, for a registry that needs a login, the name of a kubernetes.io/dockerconfigjson Secret in the namespace Attestkeep runs in; the credential itself is never stored by Attestkeep. A registry named in scan.insecureRegistries is reached over plain HTTP. If your Falco's image has changed since the version was validated, publishing validates it again first.

Your Falco picks it up through falcoctl. Attestkeep never writes to Falco. Add the reference to falcoctl in your Falco chart values, keeping your existing references, and list the file in rules_files after Falco's own rules; the editor shows these values with your repository and file name filled in:

# values for the falcosecurity/falco chart
falcoctl:
  config:
    artifact:
      install:
        refs:
          - registry.example.com/falco/my-rules:latest
      follow:
        refs:
          - registry.example.com/falco/my-rules:latest
        every: 5m
falco:
  rules_files:
    - /etc/falco/falco_rules.yaml
    - /etc/falco/my-rules.yaml

falcoctl checks the reference every follow.every. If the registry needs a login, falcoctl takes it from FALCOCTL_REGISTRY_AUTH_BASIC (registry,user,password) in falcoctl.artifact.install.env and follow.env. Deleting a file in the console removes its rules from the Rules list; what was already published stays in the registry and in every Falco that installed it, until you remove it from falcoctl there.

Validating, saving, deleting and publishing are written to the audit log as falco_rule_validate, falco_rule_file_change and falco_rule_file_publish.

What you get

In the console. Falco > Events lists events with the policy that matched and its action, filtered by text, priority, action, Falco rule, tag, namespace, pod and policy over a time range, a page at a time; the filter suggestions cover the range shown. Falco > Policies and Falco > Rules hold the policies and the Falco rules. The images list grows a Runtime column with each image's alert count for the last seven days — only once the operator has actually been sent an event, so an installation that does not use this sees no new column. The image detail panel lists the last 20 alerts for that image: time, priority, rule, namespace and pod, and Falco's own output line.

In the evidence pack. A runtime section carrying:

  • the policy set in force and its revision hash;
  • audit_entries — every policy change, pod a policy stopped and integration change in the period, each with its kind;
  • matches by policy and action, and the decisions taken, each with the tracker issue it opened, up to 500;
  • coverage: whether the integration is on, the last event and the longest silence in the period.

Two clocks are kept apart. Each decision carries event_time, Falco's own timestamp and the one to argue from, and received_at, when it reached the operator. Coverage is about the feed reaching the operator, so its last event and silence are on received_at, and coverage.clock says so. The PDF's column headings name the clock of each time column. The silence is measured from the later of the period start and the first event this installation ever received, because before the first event there was no feed to fall silent.

Ticking the raw events box in the Generate dialog — include_runtime_raw: true on POST /api/v1/evidence — adds the stored events themselves, with the same two clocks, up to 5000. Off by default.

The runtime-observed attestation is met only when the feed is configured and delivered something inside the period — a configured feed that stayed silent for a whole period reports partial, because from inside the operator a detector with nothing to say and a detector that stopped are the same silence. The rest of the package is described on compliance frameworks.

In the metrics.

attestkeep_runtime_events_total{source, priority}
attestkeep_runtime_events_dropped_total{reason="duplicate|unresolved_image|throttled"}
attestkeep_runtime_alerts_notified_total
attestkeep_runtime_rule_matches_total{rule, action}

unresolved_image is not a lost event. Falco watches the host as well as the containers on it, and an alert about a process in no container is stored unattributed — it appears in the evidence pack's runtime section with no image beside it.

How an event finds its image

An event names the image the way the runtime pulled it — nginx:1.27 — while this operator records the canonical name docker.io/library/nginx. The endpoint normalises to the second before it stores anything, using the same code path admission uses, so the two match. If the event carries no image digest, the digest of whatever the cluster last admitted under that name and tag is filled in; when there is nothing to fill in, it is left empty rather than guessed.
