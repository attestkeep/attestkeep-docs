Install

One Helm command, in the shape your cluster needs. The chart pulls straight from the registry — there is no repository to add.

Before you start

  • Kubernetes 1.27+.
  • Permission to create a ValidatingWebhookConfiguration — cluster-scoped, so cluster-admin on the first install.
  • A namespace of its own. The chart creates one.
  • Roughly 20 GiB for the bundled PostgreSQL, or the DSN of one you already run.

Verify before you install

Every release is signed on its digest. The keyed check needs nothing beyond your registry and our public key, published at docs.attestkeep.com/cosign.pub; see Releases for the keyless check and what each one proves.

curl -sO https://docs.attestkeep.com/cosign.pub
cosign verify --key cosign.pub ghcr.io/attestkeep/attestkeep-k8s:1.1.1

Install

The chart installs straight from the registry — there is no helm repo add. Three shapes, and the one you want is decided by the database and by whether the cluster can reach a public registry. Everything after this section is the same for all three.

clusterName appears in all three because it is the one value worth setting on the first install, even for a trial. It is the label every notification and every evidence document uses to say which installation it came from, and it cannot be inferred from the cluster. Nothing topological leaves the cluster, so this is a name you choose, not a hostname.

Production — a database you operate

For an installation you intend to keep: the database is yours, on your own backup and upgrade schedule. Put the DSN in a secret rather than on the command line — an inline value lands in your Helm release history and stays there.

kubectl create namespace attestkeep

kubectl -n attestkeep create secret generic attestkeep-db \
  --from-literal=dsn='postgres://attestkeep:PASSWORD@db.internal:5432/attestkeep?sslmode=require'

helm install attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  --namespace attestkeep \
  --set postgresql.enabled=false \
  --set externalDsnExistingSecret.name=attestkeep-db \
  --set clusterName=production-eu \
  --wait

With an external database the chart creates no database and no volume claim for one. The only claim left is the scanner's vulnerability-database cache, trivy.cache.persistence, 5 GiB by default. Set trivy.cache.persistence.enabled=false and that claim is gone too — the cache becomes an emptyDir and the scanner downloads the vulnerability database again after every restart, which is the trade to make on a cluster with no storage class worth using.

The policy admission decides against is a cluster-scoped CRD, not a row in that database, so a database outage does not take the rules with it: the :latest, registry, digest and break-glass gates keep refusing exactly what they refused before. What degrades is everything that needs a stored scan record, and webhook.failurePolicy decides what happens then — the trade is set out in Operations.

Evaluation — the bundled PostgreSQL

For a first look, and for Community Edition on a single cluster. One command, no database to prepare.

helm install attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  --namespace attestkeep --create-namespace \
  --set clusterName=production-eu \
  --wait

The chart brings up a single-replica PostgreSQL with a 20 GiB volume and generates its password. It is adequate for Community Edition and single-cluster evaluation, and it is not the shape for production: one replica, no backup of its own, and an upgrade of the database is an upgrade of the chart. Moving to your own database later is the production command above plus a dump and restore.

Air-gapped — no route to a public registry

For a cluster behind a perimeter. It is the production command plus the four things that otherwise reach outside: the operator image, the vulnerability database, the known-exploited catalogue, and signature verification. Air-gapped clusters covers what each of those costs.

# on a host that can reach both sides; oras copy does the same job
crane copy ghcr.io/attestkeep/attestkeep-k8s:1.1.1 \
  registry.internal/mirror/attestkeep-k8s:1.1.1
crane copy ghcr.io/aquasecurity/trivy-db:2 \
  registry.internal/mirror/trivy-db:2
crane copy ghcr.io/aquasecurity/trivy-java-db:1 \
  registry.internal/mirror/trivy-java-db:1

# the namespace, the database secret from the production profile above,
# the credential the mirror asks for, and the KEV catalogue as a file
kubectl create namespace attestkeep
kubectl -n attestkeep create secret generic attestkeep-db \
  --from-literal=dsn='postgres://attestkeep:PASSWORD@db.internal:5432/attestkeep?sslmode=require'
kubectl -n attestkeep create secret docker-registry trivy-db-auth \
  --docker-server=registry.internal --docker-username=USER --docker-password=PASS
kubectl -n attestkeep create configmap kev-catalog \
  --from-file=known_exploited_vulnerabilities.json

helm install attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  --namespace attestkeep \
  --set image.repository=registry.internal/mirror/attestkeep-k8s \
  --set postgresql.enabled=false \
  --set externalDsnExistingSecret.name=attestkeep-db \
  --set trivy.dbRepository=registry.internal/mirror/trivy-db \
  --set trivy.javaDbRepository=registry.internal/mirror/trivy-java-db \
  --set trivy.dbRegistrySecret=trivy-db-auth \
  --set kev.source=file:///etc/kev/known_exploited_vulnerabilities.json \
  --set scan.cosignOffline=true \
  --set clusterName=production-eu \
  --wait

The chart itself comes from a public registry too: helm pull oci://ghcr.io/attestkeep/charts/attestkeep --version 1.1.1 on the connected host, and install the .tgz inside the perimeter.

The chart does not mount the KEV ConfigMap for you. kev.source names a path; putting a file at that path on the scanner is a volume the chart has no value for yet, so it has to be patched onto the scanner Deployment. Leaving kev.source empty is the other option: nothing is refreshed, the catalogue already in the database keeps marking findings, and the evidence package records which version that is.

scan.cosignOffline verifies signatures against the key and skips the public transparency log, which no air-gapped cluster can reach. That is a real reduction in what a signature proves, and the air-gapped page says exactly what is lost.

Licensing still needs one route out. Activation and the daily check reach https://lic.attestkeep.com on port 443 and nothing else, which is narrow enough for a proxy with a single allowed destination; there is no offline licence format.

Confirm it is running

kubectl -n attestkeep get pods
kubectl -n attestkeep port-forward svc/attestkeep 8080:8080

Then open http://localhost:8080 and follow the first-run sequence below.

First run

The console walks a new installation through three screens, once. After that it is a normal sign-in.

  1. Enter your licence key. Every installation is licensed, the free Community edition included — paste the key from your Attestkeep account. Activation happens once and binds the key to this cluster.
  1. Create the owner account. The email and password you set here are how you sign in from now on. Whoever completes this first becomes the owner; the window closes the moment the account exists.
  1. Sign in. From here on this is the only screen you meet; authorization is always checked on the server, whatever the console shows.

You land on the security overview. What each screen does, with the same walk-through, is in Using the console.

The first images you deploy are admitted and scanned in the background; on a fresh cluster the first report takes a few minutes, and the Images page shows Unknown until it lands. If a workload must not start before its scan exists, set admissionTiming: DenyUntilScanned in the policy — see Policies.

The database builds itself

Migrations are compiled into the binary and applied on first connection, each recorded so it runs exactly once. There is no SQL for you to run and no migration step to forget on upgrade, and this holds for the bundled database and for one you operate alike.

An installation that started on the bundled database moves to your own with the same two flags the production profile uses, once the data is restored into it:

helm upgrade attestkeep oci://ghcr.io/attestkeep/charts/attestkeep \
  --namespace attestkeep \
  --set postgresql.enabled=false \
  --set externalDsnExistingSecret.name=attestkeep-db

Private registries

Nothing to configure. The operator resolves the same image pull secrets the pod references, and those on its service account, and uses them for both the scan and the signature check.

High availability

The webhook runs two replicas by default, spread across nodes by anti-affinity: one is enough to serve, two to survive a node. The serving certificate lives in a secret rather than on each replica, so a rotation reaches every replica without a restart.

Scanner replicas and volume access mode. Raising scanner.replicas above one while the scan cache is a ReadWriteOnce volume is refused at install. The volume binds to a single node, so the second replica would never schedule — better to fail at install than to leave a pod pending and let you find out later.

Uninstall

helm uninstall attestkeep --namespace attestkeep

Removing the release removes the webhook configuration with it, so admission stops being reviewed the moment it is gone. The database volume is not deleted; findings and evidence survive an uninstall unless you remove the PVC yourself.
